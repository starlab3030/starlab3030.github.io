30분 실습의 핵심 목표

System-wide Crypto Policy가 실제 Apache와 TLS에 어떻게 적용되는지 확인하고, 마지막에 X25519MLKEM768을 확인하여 Hybrid PQC Key Exchange가 사용되는 것을 검증합니다. ML-KEM 확인까지가 핵심 성공 기준이며, ML-DSA는 시간이 남을 때 진행합니다.

실습에서 집중해서 볼 세 가지

① FUTURE 적용 후 왜 Apache가 실패하는지, ② RSA 3072 인증서로 어떻게 정상화하는지, ③ TLS 1.3 연결에서 어떤 값이 PQC 적용을 증명하는지에 집중합니다.

추가 실습 목표와 사전 조건

이 추가 실습은 기존 System-wide Cryptographic Policy 본 실습을 완료한 뒤 이어서 진행합니다. 본 실습에서 FUTURE 정책 적용과 RSA 3072 인증서로 Apache 복구까지 완료한 상태에서, 같은 RHEL 10.2 시스템의 TLS 연결에 Hybrid ML-KEM이 실제 사용되는지 확인하고 시간이 남으면 ML-DSA 전자서명까지 체험합니다.

STEP 7 · 5 MIN

Hybrid ML-KEM 확인 — PQC 핵심 실습

기존 실습에서 복구한 동일한 Apache에 TLS 1.3으로 접속해, Key Exchange 단계에서 ML-KEM이 포함된 Hybrid PQC가 실제 협상되는지 확인합니다.

1-1. 사전 조건 확인

Shell · RHEL / 정책 / Apache 확인
printf '=== RHEL 버전 ===\n'
cat /etc/redhat-release

printf '\n=== 현재 Crypto Policy ===\n'
update-crypto-policies --show

printf '\n=== Apache 상태 ===\n'
systemctl is-active httpd
필요할 때만 펼쳐보는 명령어 설명
cat /etc/redhat-release
RHEL 10.2 환경인지 확인합니다.
update-crypto-policies --show
현재 정책이 FUTURE인지 확인합니다.
systemctl is-active httpd
앞 실습에서 복구한 Apache가 active인지 확인합니다.
확인 항목정상 결과다음 단계

Crypto PolicyFUTURERHEL 10.2 FUTURE 정책 확인

1-2. 실제 TLS 1.3 연결에서 Hybrid PQC 확인

Shell · Hybrid ML-KEM 확인
openssl s_client \
  -connect localhost:443 \
  -tls1_3 \
  </dev/null 2>&1 \
  | grep -E 'Negotiated TLS1.3 group|Peer signature type'
필요할 때만 펼쳐보는 명령어 설명
-connect localhost:443
현재 Apache HTTPS 포트에 접속합니다.
-tls1_3
TLS 1.3 핸드셰이크로 제한합니다.
Peer signature type
서버가 자신을 증명할 때 사용한 서명 방식을 보여줍니다.
Negotiated TLS1.3 group
클라이언트와 서버가 공유 비밀을 설정할 때 협상한 Key Exchange 그룹을 보여줍니다.
정상 결과 예시
Peer signature type: rsa_pss_rsae_sha256
Negotiated TLS1.3 group: X25519MLKEM768

서버 인증

rsa_pss_rsae_sha256

앞에서 만든 RSA 3072 인증서를 사용해 서버가 자신을 증명합니다. 현재 서버 인증은 아직 기존 RSA 방식입니다.

공유 비밀 설정

X25519MLKEM768

기존 X25519와 PQC인 ML-KEM-768을 함께 사용한 Hybrid Key Exchange입니다. 이 줄이 PQC 확인의 핵심입니다.

PQC 핵심 검증 성공

Negotiated TLS1.3 group: X25519MLKEM768이 보이면, RHEL 10.2의 FUTURE 정책 아래에서 현재 Apache TLS 연결이 기존 방식 + PQC 방식의 Hybrid Key Exchange를 사용한다는 것을 확인한 것입니다.

두 기술을 혼동하지 마세요.

ML-KEM은 통신 데이터를 직접 암호화하는 알고리즘이 아니라 공유 비밀을 설정하는 기술입니다. 핸드셰이크가 끝난 뒤 실제 HTTPS 데이터는 AES 같은 효율적인 대칭키 알고리즘으로 암호화됩니다.

이 실습에서 가장 집중해서 볼 값

Negotiated TLS1.3 group: X25519MLKEM768이 핵심입니다. Peer signature type: rsa_pss_rsae_sha256은 서버 인증이 RSA라는 뜻이고, X25519MLKEM768은 기존 X25519 + PQC ML-KEM-768을 함께 사용하는 Hybrid Key Exchange라는 뜻입니다.

STEP 8 · OPTIONAL 5 MIN

선택 확장 — ML-DSA 전자서명 체험

Step 1의 Hybrid ML-KEM 확인을 완료한 뒤 시간이 남으면 진행합니다. ML-DSA가 PQC 전자서명 알고리즘이라는 점을 파일 서명과 변조 탐지로 확인합니다.

2-1. ML-DSA-65 키 생성 및 정상 서명 검증

ML-DSA는 무엇을 확인하나요?

ML-DSA는 “누가 서명했고, 서명 이후 데이터가 바뀌지 않았는가?”를 확인합니다. 데이터를 숨기는 암호화가 아니라 신뢰성과 무결성을 증명하는 전자서명입니다.

Shell · ML-DSA-65 서명 및 검증
mkdir -p /root/pqc-lab
cd /root/pqc-lab

printf 'Hello RHEL 10 PQC\n' > message.txt

openssl genpkey \
  -algorithm mldsa65 \
  -out mldsa65-private.pem

openssl pkey \
  -in mldsa65-private.pem \
  -pubout \
  -out mldsa65-public.pem

openssl dgst \
  -sign mldsa65-private.pem \
  -out message.sig \
  message.txt

openssl dgst \
  -verify mldsa65-public.pem \
  -signature message.sig \
  message.txt
필요할 때만 펼쳐보는 명령어 설명
openssl genpkey -algorithm mldsa65
ML-DSA-65 개인키를 생성합니다.
openssl pkey ... -pubout
개인키에서 검증용 공개키를 추출합니다.
openssl dgst -sign
개인키로 message.txt에 전자서명합니다.
openssl dgst -verify
공개키로 서명이 유효하고 파일이 변경되지 않았는지 검증합니다.
정상 결과
Verified OK

2-2. 파일 변경 후 검증 실패 확인

Shell · 변조 탐지 확인
cp message.txt message-original.txt
printf 'Modified after signing\n' >> message.txt

openssl dgst \
  -verify mldsa65-public.pem \
  -signature message.sig \
  message.txt

mv -f message-original.txt message.txt
필요할 때만 펼쳐보는 명령어 설명
printf ... >> message.txt
서명된 파일에 내용을 추가하여 서명 이후 변경 상황을 만듭니다.
openssl dgst -verify
기존 서명과 변경된 파일이 일치하지 않아 검증이 실패하는지 확인합니다.
mv -f message-original.txt message.txt
테스트 후 원본 파일을 복원합니다.
ML-DSA에서 집중할 결과

원본 파일에서는 Verified OK, 변경된 파일에서는 Verification failure가 나타나면 ML-DSA 전자서명이 서명자 확인과 변조 탐지에 사용된다는 것을 체험한 것입니다.

TROUBLESHOOT

추가 실습 문제 해결

TLS 결과가 보이지 않으면 “PQC 미지원”이라고 바로 결론내리지 말고, 먼저 Apache와 TLS 핸드셰이크 상태를 확인합니다.

출력이 비어 있거나 no peer certificate available이 표시될 때

Shell · Apache / 443 / SSL 로그 확인
printf '=== Apache 상태 ===\n'
systemctl status httpd.service --no-pager

printf '\n=== 443 LISTEN 확인 ===\n'
ss -ltnp | grep ':443'

printf '\n=== SSL 오류 로그 ===\n'
tail -20 /var/log/httpd/ssl_error_log

printf '\n=== 전체 TLS 출력 ===\n'
openssl s_client -connect localhost:443 -tls1_3 </dev/null
필요할 때만 펼쳐보는 명령어 설명
systemctl status httpd.service
Apache가 실제로 실행 중인지 확인합니다.
ss -ltnp | grep ':443'
HTTPS 포트가 LISTEN 중인지 확인합니다.
tail -20 /var/log/httpd/ssl_error_log
인증서 또는 Crypto Policy 관련 오류를 확인합니다.
openssl s_client ...
grep으로 내용을 숨기지 않고 TLS 핸드셰이크 전체 출력을 확인합니다.
no peer certificate available의 의미

클라이언트가 TLS 핸드셰이크 중 서버 인증서를 전달받기 전에 연결이 실패했다는 뜻입니다. PQC 성공 메시지가 아니며, Apache 미기동·443 미LISTEN·인증서 오류·알고리즘 호환성 문제를 먼저 확인해야 합니다.

한 문장으로 정리

본 실습은 Crypto Policy가 Apache에 실제로 강제되는 과정을 먼저 경험하고, 같은 TLS 연결에서 ML-KEM 기반 Hybrid PQC Key Exchange를 확인하는 실습입니다. ML-DSA는 시간이 남을 때 전자서명 역할을 별도로 체험하는 확장 단계입니다.
